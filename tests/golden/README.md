# Golden corpus

Read-only SQL test corpus for Lume TI. Each entry pairs a TI query (`ti_sql`) with a
DuckDB oracle twin (`oracle_sql`) over the same signalk-parquet `raw` data. `lume ti
verify --oracle duckdb --corpus tests/golden` runs both and diffs them within the
tolerance rules below. This is the correctness definition (spec decisions D6, and
"Done means" in `plan/spec/01-goals.md`).

## Format (`corpus.json`)

Top-level:

```json
{
  "version": 1,
  "bucket_width_seconds": 10,
  "epoch": "2020-01-01T00:00:00Z",
  "vessels": ["vessels.urn:mrn:imo:mmsi:367000000", "..."],
  "entries": [ /* Entry, see below */ ]
}
```

Each `Entry`:

| Field | Type | Meaning |
|---|---|---|
| `id` | string | Stable id (`q<class>-<n>` or `qx-<n>`). Never reused. |
| `class` | string | One of `Q1`..`Q8` (see `plan/spec/13-benchmarks.md`). `qx-*` entries use `Q4` as their speed class but are labelled by feature in `description`. |
| `description` | string | Human description of what the query exercises. |
| `ti_sql` | string | The query `ti verify` runs against Lume TI's `telemetry`/`docs`/catalog tables. |
| `oracle_sql` | string | The DuckDB twin over the signalk-parquet `raw`/`docs`/catalog tables. Must parse and bind in DuckDB. |
| `expected_path` | string | Where part 2 writes the expected output (`expected/<id>.json`). |
| `tolerance` | object | Diff rules, see below. |

### `tolerance` object

| Key | Type | Meaning |
|---|---|---|
| `sort` | string[] | Columns to sort by before diffing (stable row order). |
| `exact` | string[] | Columns that must match **exactly**: keys (vessel, ts, title, name), set/string values, and integer counts. |
| `bsi` | object | `column → scale`. Fixed-point columns compared within ±0.5 × 10^−scale. |

`ti verify` must:
1. Run `ti_sql` and `oracle_sql`, collect rows.
2. Sort each by `sort` columns.
3. For each row and column: if in `exact`, require byte/value equality; if in `bsi`,
   require `|ti - oracle| ≤ 0.5 × 10^−scale`; otherwise ignore (oracle-only columns like
   a placeholder `score` are non-authoritative).

## Oracle conventions

- Every oracle twin buckets the parquet with
  `time_bucket(INTERVAL '10 seconds', ts, TIMESTAMP '2020-01-01')` (the `epoch` above).
- Numeric buckets use the **same aggregate** the TI `@agg` column implies, then
  `round(value, scale)` to match ingest's fixed-point.
- `set` predicates become `value_str` filters over `raw` (one row per sample); `bsi`
  predicates become `min/max/avg(value)` bucketed then compared.
- `match(kind, q)` becomes a `docs` filter on `lower(body) LIKE '%token%'` (ILIKE-style
  token match), bucketed on `ts_start`. **Approximation, documented:** this is a
  substring match, not BM25. It over-approximates in the presence of stemming/ranking;
  queries here use single-token or OR-of-two-token patterns so the planted-keyword
  oracle matches BM25 hits. See `paths.md` for the planted keywords.
- Geo (`within_nm` / `in_bbox`) becomes a haversine / lat-lon range filter over the
  bucketed `arg_max` lat/lon. **Approximation:** `within_nm` uses an equirectangular
  approximation `111.195 * sqrt(Δlat² + (Δlon·cos(lat))²)`; TI refines by haversine on
  materialized rows. Boundary points within the (small) approximation error are excluded
  from expected outputs in part 2.
- `intervals(...)` becomes a `GROUP BY vessel` over the same predicate with
  `HAVING (max-min) >= min_len` and a `count(*) AS buckets`. **Approximation:** the
  oracle groups the whole matching set as one interval per vessel (no gap-merge of
  `max_gap`). Part 2 corrects expected outputs for `max_gap`; part 1 documents the
  semantics.

## Pushdown coverage

Each pushdown row in `plan/spec/07-query.md` is exercised by at least one entry:

| Pushdown row / feature | Entry ids |
|---|---|
| `vessel =` / `IN` | q1-001, q2-004, qx-012 |
| `ts` comparisons, `BETWEEN` | q3-005, q3-001 |
| `set_col = / != / IN / NOT IN` | q2-001 (`=`), q2-004 (`!=`), q3-006 (`OR`), q2-006 (`NOT IN`), q2-003 (`IN`) |
| `bsi_col <op> literal`, `BETWEEN` | q2-002 (`BETWEEN`), q3-007 (`BETWEEN`), q2-005 (col-vs-col, unsupported), q4-001 (`>`), q1-002 (`@last`) |
| `col IS [NOT] NULL` (presence) | q2-003, q3-005 (count col), q1-007 (count field) |
| `match(...)` | q6-001..q6-006, q2-001, q7-005 |
| `in_bbox`, `within_nm` | q7-001..q7-006 |
| `AND`, `OR`, `NOT` of the above | q2-003 (`NOT`), q3-006 (`OR`), q2-001 (`AND`) |
| anything else (col-vs-col, arithmetic) | q2-005, qx-003 |

SQL features: joins (qx-001, qx-010 self-join), CTEs incl. recursive (q4-004, qx-004),
correlated/scalar subqueries (qx-003), window functions (q4-003, qx-008), `UNION`/`INTERSECT`/`EXCEPT`
(qx-002, qx-007, qx-006), `CASE`/`GROUP BY`/`HAVING` (qx-005, qx-009), `ORDER BY`/`LIMIT` (qx-011).

Motivating query: q2-001. PV-1 energy queries: q5-002 (electric-only motoring),
q4-006/qx-012 (energy aggregation).
