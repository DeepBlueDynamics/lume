# D52 — Append-only DocStore persistence

Status: **APPROVED by Annual Echidna on 2026-10-08 under the user's standing autonomy; implementation in A13.** No new dependencies or public DocStore/SQL schema changes.

## Problem and proposal

Before D52, crates/ti-store/src/docs.rs serialized all documents on every changed upsert/delete/reconcile. commit() cleared its file stamp, so the next write also reopened and parsed the whole snapshot. A13 replaces that persistence with one active append-only segment, docs/documents.log (segment 0), with a 24-byte versioned magic/generation/checksum header and CRC32-protected JSON transaction frames. Each frame has a 16-byte length/payload-checksum/header-checksum prefix; its header checksum is verified before trusting the payload length. Reuse serde_json and the existing crc32fast dependency. Each changing public mutation is one frame containing its upserts and tombstones, followed by sync_all; caller batching remains upsert_all/reconcile. Validate and stage the whole mutation before append, then publish memory/version only after successful sync. Identity, replacement, missing-delete and unchanged-upsert semantics stay unchanged.

Rebuild the ordered in-memory (vessel, id) index on open. Track generation and the last complete offset; refresh reads only new committed frames, and own commits update that cursor rather than forcing a full reload. Check the fixed-size generation header and length on refresh, so atomic compaction is detected even with equal sizes or coarse mtimes. A generation change rebuilds the index; refresh/version still reflect observable document changes, preserving text-cache invalidation.

Serialize append, recovery and replacement using a separate persistent docs/documents.lock and standard-library file locks, which are [stable since Rust 1.89](https://doc.rust-lang.org/std/fs/struct.File.html#method.lock). Acquire the lock before refreshing an external writer's tail and hold it through durability/publication; release handles before replacing the log on Windows. Readers must not see partially published batches, and two DocStore instances must not overwrite one another's updates. Normal reads use a shared lock; torn-tail repair upgrades through a fresh exclusive acquisition and rechecks state. Preserve read-only access to a complete store; repair/migration errors must remain explicit when write permission is unavailable.

## Recovery, migration and compaction

A frame commits a whole API mutation. Check lengths against remaining file bytes before allocation and verify checksums before applying any operation. On open, truncate and sync an incomplete final frame to the last good boundary under the writer lock. An incomplete final frame or a final frame with an invalid payload checksum is uncommitted; a bad frame-header checksum fails explicitly because its boundary cannot be trusted, except when every byte from that offset to EOF is zero (an allocated, unwritten suffix after power loss). A13b scans that suffix in 4 KiB chunks and recovers it as a torn tail; any non-zero garbage remains corruption. Corruption in earlier committed frames or valid-checksum invalid JSON fails explicitly rather than discarding history. On write/sync failure, invalidate the local cursor and reload under the lock before another operation; do not publish optimistic in-memory changes. Recovery may observe the old or complete new transaction after an unacknowledged write, never a partial batch.

When obsolete operations (superseded upserts plus tombstones) exceed 50% of logged operations, compact under the same lock into a sibling temporary file containing only current live documents, with generation + 1. Sync the temporary file, atomically rename over the active segment, and sync the parent directory on Unix. Never delete the old segment first. Ignore orphan temporary files on recovery. This bounds rewrite cost amortized across changes; telemetry shard seals need not force a document rewrite. Compaction failure must not turn an already acknowledged append into an ambiguous failed mutation: retain valid log state and report maintenance failure separately.

For legacy stores, validate documents.json, make a synced documents.json.bak without overwriting an existing backup, build and sync segment 0, then atomically publish it and sync the directory. Until log publication the legacy snapshot remains authoritative; afterward the log is authoritative. Retain the backup, retire the legacy active JSON only after publication, and retry interrupted finalization safely on subsequent open. Do not keep rewriting a compatibility JSON snapshot. Older Lume binaries cannot safely write a migrated store without explicit restoration from backup.

Opening a legacy store migrates it even through read-only commands (`lume ti query`, `lume ti explain`, or `TiEngine::open`); migration acquires the document writer lock. Copy legacy fixtures into an owned lane before opening them for profiling.

## Acceptance after approval

- Existing upsert/delete/reconcile, ordering, version and docs-schema tests, plus two-instance/cross-process refresh and writer tests.
- Migration and interrupted migration, torn final frame versus earlier corruption, and failed append/sync without partial memory publication.
- Kill a child process at controlled compaction phases (partial temp write, synced temp before rename, and replacement before directory sync); reopening preserves all committed documents and remains writable. Test hooks stay test-only.
- Resource polling, SQL docs, match(), vessel isolation and external text-cache refresh regressions. Update the two resource tests that inspect the old persistence filename.
- Same-process microbenchmark of the old JSON strategy versus append+fsync at 1k/10k/50k live documents, same document size, filesystem, warm-up and update count; report median/p95 per-upsert and bytes written, including amortized compaction separately.
- Rust 1.96 locked TI tests, strict clippy and scoped formatting; target below 8 GiB and final cleanup. Implementation and the 13 DocStore tests are complete. Measured update and amortized compaction results are in [the A13 report](../design/docstore-append.md); remaining gate results are recorded there after completion.
