 Lume Telemetry Index — Build Spec

   Oct 5, 2026 · ​@Tom

 Purpose and goals

  We are adding a bitmap-indexed, SQL-queryable telemetry index to Lume ("Lume TI"). It
  sits beside Signal K and signalk-parquet, so one query can combine numeric thresholds,
  discrete states, events, geography and full text across a fleet, and return in milliseconds.
  It applies Pilosa/FeatureBase ideas (roaring bitmaps, bit-sliced indexes, time-sharded
  column space) in Rust inside Lume. Apache DataFusion supplies the SQL engine.
  The query it exists to answer:

     SELECT vessel, date_bin(INTERVAL '10 minutes', ts) AS win,
     max("environment.wind.speedTrue@max")
     FROM telemetry
     WHERE "propulsion.port.state" = 'started'

        AND "electrical.bilge.pumpCycles" > 3
        AND "environment.wind.speedTrue@max" > 12.9 -- 25 kn in m/s
        AND match(notes, 'leak OR water')
        AND ts > now() - INTERVAL '90 days'
     GROUP BY vessel, win;

 Goals

   1. G1 Full SQL over Signal K. Full read-only SQL over bucketed telemetry and raw
      samples, for one vessel or a fleet: joins, CTEs, subqueries and window functions.
      Served over MCP, HTTP, CLI and the Postgres wire protocol, so psql, Grafana and
      DBeaver connect unchanged.

   2. G2 Fast selective queries. Queries with four or more predicates run in bitmap space.
      See Benchmarks for targets on a Raspberry Pi 5 and on a shore host.

   3. G3 Text and telemetry in one column space. match() over notes, logbook entries,
      notifications and Meridian VHF transcripts is just another bitmap filter.

   4. G4 Derived and rebuildable. Raw truth stays in signalk-parquet and the delta stream.
      The index can be dropped and rebuilt at any time.

   5. G5 Agent-first. Schema introspection, natural-language path resolution through Lume
      hybrid search, and an explain that says what was pushed down.

   6. G6 Fleet-native. Each vessel indexes at the edge. Sealed shards replicate to shore over
      intermittent links, and a shore node queries every vessel.

   7. G7 Plugs into the boat's Pi computer. One-click install on a Hat Labs HALPI2 running
      HaLOS (its container app store), and on any Raspberry Pi running OpenPlotter (the
      Signal K App Store). No compiler, no cloud, and no change to OpenCPN or the NMEA
      2000 network. Pi 4 (4 GB) is the floor; the CM5/Pi 5 class is the target.

 Non-goals for v1

      Replacing Signal K storage or the History API's provider. The History API adapter is a
      stretch goal.
      Raw-sample fidelity in the bitmap index. Raw samples are reached through a federated
       raw table that reads Parquet directly.
      Writes through SQL (no INSERT, UPDATE or DELETE).
      Clustering or consensus. Every node is single-process, and fleet scale comes from
      shard federation.
      Sub-second alerting. Rules and alarms stay in Signal K.
      Stored procedures, triggers or user-defined schemas. Queries get full read-only
      DataFusion SQL, and pushdown changes only speed, never which SQL is accepted.

 Done means

      The golden query corpus (≥ 60 queries) returns results identical to the DuckDB oracle,
      within fixed-point tolerance.
      Benchmark targets are met on both reference machines.
      An agent connected only to Lume's MCP server can answer the motivating query from
      a plain-English question.
      On the pilot vessel's HALPI, Lume TI installs from the Signal K App Store in under 30
      minutes. An energy query then runs from psql and from the plugin's webapp.

 Pilot vessel (PV-1)

  PV-1 is the v1 reference boat: the first real dataset, the first install, and the test of whether
  Lume TI really plugs into a Pi in an afternoon. She is a privately owned 16 m aluminium
  hybrid catamaran in fit-out, which replaces the owner's previous boat ("the previous
  boat" below). Her electronics were still being chosen as of February 2026, so ingest has to
  work with whatever ends up on the NMEA 2000 backbone.

Rules enforced in ti-serve and the container or systemd unit:

    Hard cap. MemoryMax=1.5G on the whole Lume TI unit. A query that needs more fails
    with a hint to narrow ts ; it never swaps the box.
    Admission. DataFusion runs with target_partitions = 2 on the boat. One heavy
    query runs at a time, others queue, and the default timeout is 30 s.
    Thermal. The HALPI2 is passively cooled, and its host daemon reports SoC
    temperature. Above 75 °C, background jobs pause and query threads drop to 1.
    Shutdown. On the HALPI shutdown signal (power-button double-click or the host
    daemon), Lume TI flushes the WAL first. A power cut costs at most 60 s of buckets,

    Contention test. Gates M6 (see Benchmarks).

 System architecture

  Lume TI is four layers in one Rust binary: ingest, store, query and interfaces. It runs on
  every vessel, and sealed shards are the only thing that moves to shore.

  Lume TI architecture · 4 layers, one binary per vessel

  The bitmap evaluator (highlighted) is the only place Predicate IR meets roaring rows,
  which is why it is the contract every lane builds against. Raw samples bypass the index
  entirely through the federated raw table over Parquet.

Data model

Every column is one time bucket for one vessel. Every field is a set of roaring-bitmap rows
over those columns. A shard is one vessel × 65,536 consecutive buckets, so each row in a
shard fits exactly one roaring container (≤ 8 KB).

Column space

    Bucket width W : configurable per deployment, default 10 s. It is fixed once a store is
    created, and changing it means a rebuild.
    Bucket index: b = floor((t − EPOCH) / W) , with EPOCH = 2020-01-01T00:00:00Z .
    Column id: col: u64 = (vessel_ord as u64) << 32 | b . A 32-bit bucket index
    holds about 1,360 years at 10 s.
    Shard key: (vessel_ord, b >> 16) . At 10 s a shard spans 7.58 days, and a year is
    about 48 shards per vessel.
    Local column: b & 0xFFFF , stored in a RoaringBitmap (u32) per row per shard.
    Vessel ordinal: a dense u32 assigned by the vessels catalog and keyed by Signal K
    context URN (e.g. vessels.urn:mrn:imo:mmsi:367000000 ). The local vessels.self
    resolves to its URN at ingest.

BSI encoding

    Fixed-point: i = round(v × 10^scale) . Scale comes from the path's Signal K
     meta.units through the registry below, and a per-path override is allowed.
    Sign-magnitude: rows exists , sign , then bit[0..depth) . Depth grows when a
    value exceeds the current range. A wider depth only adds rows and never rewrites old
    ones.
    Comparisons: use the O'Neil/Quass bit-sliced range algorithm, as Pilosa did. It takes
    one pass over depth rows, AND/OR/ANDNOT only.
    Tolerance: the oracle comparison allows ±0.5 × 10^−scale.

Bucket aggregates

Each numeric path keeps running count , sum , min , max and last per bucket. The
bucket closes into BSI fields named path@agg . The bare path name is an alias for @mean .

    Default profile: @mean , @min , @max .
     slow profile: @last only. Used for paths with a median sample interval ≥ W , such as
    tank levels.
    Opt-in: @last and @count on any path.

Derived fields

These are computed at bucket close from rules in ti.toml :
    Transitions: e.g. propulsion.*.state changing to started becomes a count field …
    @starts .
    Edge counts: a boolean path's rising edges per bucket, e.g. bilge pump cycles.
    Notifications: each notifications.* path becomes a set field over state values
    ( normal , alert , warn , alarm , emergency ), plus a count of raises.

Multiple sources

    The path's value comes from the preferred source, using Signal K source priorities
    when configured, otherwise the first source seen.
    Every source that reported in the bucket is recorded in a path$source set field, so
     WHERE "navigation.speedOverGround$source" = 'n2k.115' works.
    Per-source values are a v2 option.

Text mapping

Notes (Resources API), logbook entries and notification messages are indexed as Lume
documents with ts_start and an optional ts_end . match(notes, q) runs Lume BM25
over the docs of that kind. Each hit becomes the bucket columns its time range covers.
The resulting bitmap is cached per (q, shard) with an LRU.

 Catalogs

  These are stored as JSON in the store root and exposed as SQL tables:

        vessels(ord, urn, name, mmsi, first_seen, last_seen)
        paths(path, field, agg, type, units, scale, depth, description,

      first_seen, last_seen) , with description from Signal K meta and the spec

        shards(vessel, shard_no, ts_from, ts_to, sealed, bytes, hash)

 Size budget

      Worst case: a dense BSI field at depth 16 is 18 rows × 8 KB × 48 shards ≈ 6.9 MB per
      vessel-year at 10 s.
      Typical boat: 120 numeric paths under the default profile is about 360 fields, so ≤ 2.5
      GB per vessel-year worst case. Run containers and sparse paths bring the expected
      size to 0.6–1.0 GB.
      Pi retention: default 2 years. Older shards live only on shore.

 Ingest pipeline

  Live deltas and Parquet backfill feed the same bucketer. Buckets close on a watermark
  and land in shards through a write-ahead log, and a shard seals once it is entirely in the
  past.

 Sources

   1. Live. A Rust WebSocket client connects to ws://<host>:3000/signalk/v1/stream?
      subscribe=none . It then sends {"context":"vessels.self","subscribe":
      [{"path":"*","period":1000,"policy":"instant"}]} and

        {"context":"vessels.self","subscribe":

      [{"path":"notifications.*","policy":"instant"}]} . Auth uses a Signal K device
      token from an access request, stored in ti.toml .
   2. Backfill. Reads signalk-parquet files with the arrow-rs parquet crate. It maps
       received_timestamp / signalk_timestamp , path , value and value_* columns, and
      skips files whose content hash is already in the manifest. On HaLOS Marine, history
      lives in the bundled InfluxDB rather than in Parquet. A second backfill reader exports it
      by measurement and time range, and maps it to the same tuples.

   3. Meta. On connect and every hour, it fetches GET /signalk/v1/api/vessels/self to
      read meta (units, displayName, description, zones) into the path registry.

   4. Documents. It polls GET /signalk/v2/api/resources/notes every 60 s. It also takes
      logbook plugin entries when that plugin is installed, and notification messages from
      the live stream. Each becomes a Lume document with a time range.

 Stages

   1. Decode. Turn each delta into (context, path, $source, timestamp, value) tuples,
      using the update's timestamp and falling back to receive time if it's missing or skewed
      by more than 5 min.

   2. Normalize. Flatten object values. navigation.position becomes .latitude ,
       .longitude plus H3 cells, and {value: {a, b}} becomes path.a , path.b . Drop
      paths matching the deny-list (default: *.ais.* raw sentences and design.* ).

   3. Classify. Map numbers to bsi , and strings, booleans and enums to set . Objects are
      flattened and recursed. A path's first classification is sticky, and a later type change
      logs and creates a path#2 field.

   4. Bucket. Keep per- (vessel, path) accumulators keyed by bucket index: count , sum ,
       min , max , last , sources seen, and edge or transition counters.

   5. Close. A bucket closes when the watermark (max event time − 30 s lateness) passes
      its end. Closing emits BucketRecord s (see Fleet workstreams).

   6. Write. Append to the per-vessel WAL (length-prefixed bincode with CRC32), then
      apply to in-memory shard rows. Flush dirty shard rows to disk every 60 s or every 50k
      records, then truncate the WAL to the flush point.

   7. Seal. A shard seals once now − shard_end > 1 h . Sealing writes immutable per-field
       .rbm files (roaring portable format), computes a BLAKE3 hash over the field files, and
      updates the manifest.

 Late and re-ingested data

      Data arriving after its bucket closed but before the shard seals re-opens that bucket
      for that field. This is a clear-and-rewrite, since BSI rewrite clears every row's bit for the
      column first.
      Late data after the shard sealed goes to a repair queue. A repair rewrites the shard
      into a new version and changes its hash. Shore picks the new version up by hash.
      Backfill always uses the clear-and-rewrite path, so it is idempotent.

Query layer

DataFusion parses, plans and executes SQL. Lume TI is a TableProvider that takes
pushed-down filters, evaluates them as bitmap operations per shard, and materializes
only the surviving rows into Arrow. Pin one DataFusion major version per release, and
upgrade only behind the golden corpus.

SQL coverage

The SQL is full read-only SQL: anything DataFusion accepts runs against every table here.
Pushdown decides only how fast a query runs, never whether it runs. Supported:

    Joins of any kind across telemetry , docs , raw and the catalogs
    CTEs, including recursive ones
    Correlated and scalar subqueries
    Window functions ( lag , lead , row_number , framed rolling aggregates)
     UNION , INTERSECT , EXCEPT
     CASE , GROUP BY / HAVING , ORDER BY / LIMIT
    DataFusion's scalar, aggregate and time functions ( date_bin ,
     approx_percentile_cont , and so on), plus the Lume TI functions below

INSERT, UPDATE, DELETE and DDL are rejected with an error that names the table as
derived.

  -- Window function over pushed-down rows: hours where house SOC fell faster
  than 5 %/h
  WITH h AS (

      SELECT date_bin(INTERVAL '1 hour', ts) AS hr,
                  avg("electrical.batteries.house.stateOfCharge") AS soc

      FROM telemetry
      WHERE ts >= now() - INTERVAL '14 days'
      GROUP BY hr),
  d AS (
      SELECT hr, soc, soc - lag(soc) OVER (ORDER BY hr) AS delta FROM h)
  SELECT * FROM d WHERE delta < -0.05 ORDER BY hr;

The ts filter is pushed down. The CTE, the window and the outer filter run in DataFusion
over the rows that survive it.

Execution

1. Plan. Translate pushed filters into the Predicate IR (see Fleet workstreams). Prune to
    candidate shards using the vessel and ts bounds plus the manifest.

2. Evaluate. Each shard is a partition in DataFusion. Evaluating the IR yields a
     RoaringBitmap of local columns.

3. Materialize. Iterate the set bits in batches of 8,192. For each projected column, read
    values: set columns do a row-membership lookup per value, and bsi columns
    reconstruct the integer from depth rows and divide by 10^scale. Emit a RecordBatch .

4. Stream. Batches go to DataFusion operators (aggregate, sort, join) unchanged.

Aggregate rewrites (M4)

A physical optimizer rule replaces Aggregate(Scan) with a BitmapAggregateExec when
every aggregate is one of the following, over pushed filters only:

     count(*) , computed as bitmap cardinality
     count(col) , computed as cardinality of filter AND presence
     sum , min or max of a bsi column, using the bit-sliced algorithms

The GROUP BY must be absent or limited to vessel and date_bin(ts) . Group windows
become column-range masks. The target is ≥ 10× faster than materialize-then-aggregate
on year-long windows.

Explain

EXPLAIN and ti_explain print the DataFusion plan plus a Lume TI section. It lists shards
pruned versus scanned, each conjunct's pushdown class, bitmap cardinality after each
step, and the materialized row count. Agents use this to rewrite slow queries.

 Fleet topology

      Each vessel runs lume ti ingest plus serve . Sealed shards are immutable and
      content-hashed, which makes them the unit of replication.
       lume ti sync diffs the local manifest against shore and ships missing shard versions.
      It resumes chunked uploads, so it tolerates Starlink and cellular drops.
      The open shard ships as WAL tail segments every 5 min when online, so shore lag stays
      at 5 min or less.
      The shore node mounts all vessels' shards. Its telemetry table spans every vessel
      ordinal, and vessel ordinals are re-mapped by URN at import.

  that, every lane builds against traits and fixtures and never waits on another lane's
  implementation. All crates live in the Lume workspace under crates/ti-* .

  against that same DuckDB baseline on two reference machines. The targets below are
  proposals to confirm at M0, not measurements.
