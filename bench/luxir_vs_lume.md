# Luxir vs. Lume Benchmark: BEIR SciFact and TREC-COVID

This benchmark compares **Luxir** (v0.1.0) and **Lume** (v0.12.2) on the BEIR test splits of SciFact and TREC-COVID. Both systems were evaluated on identical host hardware using Docker Linux containers under strict parity constraints (`--cpus 8 --memory 8g`, loopback binding, shared local Shivvr embeddings, dedicated Linux named volumes, and host execution serialization).

---

## 1. Test Environment & Fairness Setup

### Hardware & Container Constraints
- **Host**: 24-core x86_64 host running Windows 11 and Docker Desktop 29.4.0 (WSL2 backend).
- **Container Limits**: Both engines run in separate Linux containers constrained to `--cpus 8 --memory 8g`.
- **Storage Subsystem**: Dedicated Linux Docker named volumes (`luxir-bench-data` for Luxir, mounted at `/var/lib/luxir_data`, and a corresponding Linux volume for Lume) are used for index storage. Neither engine uses Windows host bind mounts for its index directory, eliminating VirtioFS/9p translation overhead.
- **Network Path**: Both engine containers join the user-defined Docker bridge network `luxir-bench-net` (`http://luxir-bench:9400` and `http://lume-engine:5863`), with client queries routed directly across container hostnames. Host port publications (`127.0.0.1:9400`) are retained exclusively for manual health inspection.
- **Transport & Client**: Shared stdlib HTTP client ([`JsonClient`](luxir/http_runner.py#L13-L58)) using persistent HTTP keep-alive connections (`TCP_NODELAY`), evaluating 8-worker and 16-worker wall-clock concurrency with driver CPU accounting.
- **Embedding Alignment**: Hybrid runs for both engines use identical 768-dimensional dense vectors generated by the local Shivvr daemon (`gtr-t5-base`, cosine metric) served at `http://host.docker.internal:8085/embed`.

### Software Under Test
- **Luxir**:
  - Version: `0.1.0 (x86-64-v3, AVX2)`
  - Binary: Prebuilt Linux x86_64 (`82,383,560` bytes / 82.38 MB, SHA-256 `5bcfe74159b5abba9bbafffeb6a224483cc8f8f37ad85d76568627555b3a434f`)
  - Schema Configuration: `text` configured with parent `_t` (Unicode UAX#29 word tokenizer, NFKC case/accent folding, English possessive removal, KStem stemming, Lucene BM25 scoring). Hybrid mode adds `embedding_v: {type: "vector", dims: 768, metric: "cosine"}`.
  - Query Interface:
    - BM25: `POST /collections/<name>/_search` with `{"query": {"match": {"text": "<query>"}}, "limit": 100, "get_scores": true, "fields": ["id"]}`.
    - Hybrid: RRF fusion `POST /collections/<name>/_search` with `ops.hybrid.fusion` combining lexical BM25 and vector KNN (k=60).
- **Lume**:
  - Version: Released `v0.12.2` (commit `5d88268`, Linux x64 binary `102,273,888` bytes / 102.27 MB).
  - Indexing: Plain text indexing splitting into markdown sections, using `MiniRoaring` posting lists and prime signature filters.

## 2. Benchmark Contract & Measurement Protocol

The evaluation is managed through a shared test harness ([`prepare.py`](luxir/prepare.py), [`http_runner.py`](luxir/http_runner.py), and [`score.py`](luxir/score.py)):
1. **Datasets**:
   - **SciFact**: 5,183 documents, 300 test queries, 339 qrels.
   - **TREC-COVID**: 171,332 documents, 50 test queries, 66,336 qrels.
2. **Scoring Conventions**:
   - **nDCG@10**: Linear relevance gain, log2 discount, depth 10.
   - **Recall@100**: Positive relevance judgments (grade > 0), depth 100.
   - **R_cap@100**: Positive hits divided by $\min(100, |\text{relevant}|)$, matching standard BEIR reporting for deep-qrel collections like TREC-COVID.
   - **MRR@10**: Reciprocal rank of first positive relevance judgment, depth 10.
   - **Macro-averaging**: Unretrieved queries receive zero score across all quality metrics.
3. **Latency Protocol**:
   - One complete warmup pass over all test queries.
   - Three timed passes sequentially recording per-query elapsed time in milliseconds via high-resolution monotonic timer (`time.perf_counter()`).
   - Per-query latency is the median of the three passes; report percentiles (p50, p95, p99) use linear interpolation.
4. **Throughput Protocol**:
   - 8 concurrent workers querying continuously for 60 seconds against a warm server, followed by 16 concurrent workers for 60 seconds to detect client/driver saturation.
   - Reports achieved QPS, total requests, error count, and driver process CPU consumption.
5. **Host Serialization Protocol**:
   - Zero concurrent host load: only one timed job executes on the 24-core host at any time using explicit `START`/`DONE` locks over Hyperia mail.

### Key Observations
- **Indexing Speed**: Luxir indexed the 171,332 TREC-COVID documents in 7.10 seconds (>24,100 docs/sec) in BM25 mode on the named volume. For SciFact, full-text indexing completed in 0.31 seconds (~16,700 docs/sec) compared to Lume's 25.01 seconds (**80x speedup**).
- **Index Compression**: Luxir's committed BM25 index on disk is 8.27 MB for SciFact (vs. 57.80 MB for Lume, a **7.0x smaller footprint**) and 182.81 MB for TREC-COVID.
- **Memory Footprint**: Peak RSS during full TREC-COVID BM25 indexing remained under 103 MB, settling to 36.49 MB idle memory after flush and segment commit.

## 6. Relevance Audit & Lexical Pipeline Analysis

A detailed source-level audit was conducted to analyze why Luxir achieves **0.6793 nDCG@10** on SciFact BM25 compared to Lume's **0.6447 nDCG@10** (+0.0346 advantage). Full details and source citations are documented in [`bench/luxir/relevance_audit.md`](luxir/relevance_audit.md).

### Summary of Discovered Drivers
1. **Absence of Stemming in Lume** (`src/bm25.rs`):
   Lume has no stemmer. Scientific claims frequently inflect query terms differently than document abstracts (e.g. `biomaterials` vs. `biomaterial`, `inhibits` vs. `inhibit`). Luxir uses **KStem** (`src/luxir/analysis/KStemmer.cpp`), maintaining dictionary integrity while conflating morphological variants.
2. **The Markdown Header "Introduction" Title Defect** (`src/bm25.rs#L235`, `L139`):
   Lume defaults `title_weight: 2.0` and `body_weight: 1.0`. However, `parse_markdown` only extracts titles from lines beginning with Markdown headers (`#`). In BEIR plain text, all documents receive the literal title `"Introduction"`. As a result, `title_score` is 0.0 for all queries, and title terms in the body only receive body weight (1.0) rather than the intended 2.0 weight.
3. **Coordination Factor Penalty** (`src/bm25.rs#L695-L697`):
   Lume penalizes documents that do not match all query terms via `total_score *= coord`. For long scientific hypothesis queries (12–18 words), documents matching 8 core domain keywords are heavily discounted if they miss 2 peripheral terms.
4. **Tokenizer Splitting on Hyphenated Medical Terms** (`src/lib.rs#L647`):
   Lume splits strictly on non-ASCII alphanumeric characters, fragmenting terms like `SARS-CoV-2` and `IL-6` into generic pieces. Luxir uses Unicode Standard Annex #29 (`unicode_word`) segmentation.

## 7. Architectural Differences & Talking Points

1. **Standalone Search Engine vs. Embedded Database Engine**:
   - **Luxir** is a purpose-built, high-throughput search daemon in modern C++20. It excels at lexical quality, instant indexing (>24,000 docs/sec), rich search primitives (phrase with slop, full booleans, multi-select facets), and raw query latency (0.33–1.24 ms p50).
   - **Lume** is a versatile multi-model Rust engine integrating full-text BM25 search, knowledge-graph entity walks (SKG), time-series stream aggregation, and a complete relational SQL interface.
2. **Platform Portability**:
   - **Lume** runs natively on ARM64 and low-power edge devices (Raspberry Pi 5).
   - **Luxir** is firmly tied to x86-64 server architectures with AVX2/BMI2 hardware acceleration.
3. **Storage Parity Finding**:
   - Running index workloads on native Linux Docker named volumes (`luxir-bench-data`) eliminated VirtioFS/9p Windows bind mount translation overhead, cutting indexing wall clock from 8.42s to 7.10s and increasing throughput from 11.77 QPS to 38.45 QPS on TREC-COVID.
